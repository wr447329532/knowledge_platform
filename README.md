文件共享和知识管理平台
=================================

本项目是在 `vscode` 目录下从 0 开发的**文件共享和知识管理平台**，采用 **Python + FastAPI** 后端与 **Vue 3 + Vite** 前端。  
**最后更新：2026 年 4 月 23 日**

**当前已实现：**

- 用户系统：**邮箱登录**、管理员创建用户（邮箱必填，用户名仅用于显示）、强密码策略（8 位以上，含大小写、数字、特殊字符）
- 文件库：创建 / 编辑 / 删除 / 软删除（回收站），按文件库管理文件；支持**部门库**（所属部门成员可访问）；**新建资料库默认关闭非拥有者下载**（`allow_download` 默认 `false`），库主可在编辑中开启；支持**资料库移动**（在允许的父级范围内调整挂载位置）；支持**多级子资料库**：在一级文件库下可创建**二级、三级**子资料库（父子关系由 `parent_id` 维护），进入一级库后在根路径可查看与管理子资料库列表
- 文件上传 / 下载 / 版本历史 / 重命名 / **回收站**（已删除的文件库与文件统一列表展示，恢复、彻底删除，仅手动彻底删除才会永久移除）
- 文件版本历史已支持显示上传者（版本号、大小、上传者、上传时间）
- 文件版本历史支持删除单个版本：删除后进入回收站（`历史版本`），可恢复或彻底删除
- **版本匹配上传**：上传前自动提取关键词并搜索库内可能相关文件；有结果时在上传弹窗内进行版本确认（作为新版本或新文件），无结果直接上传；支持多文件队列逐一确认。已增强“文件名后缀数字/字母”场景（如 `报告1`、`报告A`、`报告(1)`）的版本识别能力；可执行/脚本类文件（如 `.exe`、`.bat`）会被拒绝上传
- 在线预览：站内受控预览页（`/#/preview`），支持图片、PDF、文本（txt/md/json 等）
- **部门管理**：部门树、部门库、新建子部门、负责人展示、部门搜索
- **共享文件库**：基于库级 ACL 的「我分享的文件库 / 分享给我的文件库」视图，统一展示库名称、共享范围（公开/部门/指定成员）与文件库类型（个人库/部门库/公开库）
- **共享文件（单文件）**：后端接口保留；前端“单文件分享”按钮已先行隐藏（后续成熟后再评估重新开放）
- **我的文件库**：列表与网格视图、排序（最近修改/文件名/大小/创建时间）、三点操作菜单（含**移动资料库**）、长文件名省略；顶栏支持**新建子资料库**（当前在一级库内时挂到该库下）；**顶栏全局搜索（文件库）**按名称/描述匹配时包含当前用户可访问的二级、三级子资料库；在部门视图下搜「文件库」亦包含该部门下的子资料库；首页列表与部门文件库列表仍为一级根库分页（后端 `roots_only` 默认 `true`）；从**部门文件库**经顶栏搜索进入某个资料库后，点击面包屑中的资料库名称退出当前库时会**同步清空顶栏搜索**，回到该部门的资料库列表（不再误留在「我的文件库」全局搜索视图）
- **统一权限模型（库级 ACL）**：
  - 访问优先级：超级管理员 › 库拥有者 › 库成员 › 部门库成员 › 公开库
  - `Library.visibility = private / members / department / public` 控制库可见范围
  - `LibraryMember` 维护库成员及角色（只读 / 读写）；`allow_download` 控制非拥有者是否可下载
  - 后端 `has_library_access / can_access_file / can_download_file / get_accessible_library_ids` 统一判定访问与下载权限
  - 高管（`executive`）默认可预览、可下载（前提是对文件具备访问权限）
  - 修复了「无部门用户误看到全部部门库」的权限漏洞（无部门或无效部门的普通用户不再拥有全局访问）
- **账户管理（普通用户）**：
  - 右上角用户头像下拉菜单进入账户设置、系统管理（仅管理员）、部门管理（仅部门负责人）、退出登录；侧边栏不再保留账户/系统管理入口
  - 个人信息：显示并支持修改姓名，邮箱和所属部门只读（由管理员维护），保存后即时生效并有成功提示
  - 安全设置：支持修改密码（校验原密码 + 强密码规则），并可查看动态安全信息（账户状态、上次登录时间/IP、上次修改密码时间）
- 审计日志：记录上传、删除、恢复、分享、预览、下载等操作，支持按用户与操作类型模糊筛选（仅管理员可查）；支持**导出日志**为 Excel 下载到本地
- 系统管理：
  - **用户管理**：启用/停用、重置密码、分配部门、管理员标记
  - **部门管理**：树形表格、存储统计占位、部门负责人
  - **存储管理（新）**：按部门 / 用户 / 文件类型聚合存储使用，支持配额调整；部门维度“增长趋势”已改为动态计算（最近 7 天新增文件数 vs 前 7 天），并在存储页自动刷新。当前默认策略为 `2TB` 总配额 + `20%` 预留池 + 部门基础配额（`120GB`）+ 人数占比分配浮动配额；用户未设置配额时显示“未设置”
  - **通知管理（新）**：通知模板、发送历史、通知开关、管理员一键群发通知

**后续规划：** 新建资料库更细粒度权限设置（角色 / 继承策略）、全文搜索、本地 LLM 知识问答等。

快速开始
--------

> ⚠️ **强制安全要求：必须修改 JWT_SECRET_KEY**
>
> 后端使用 JWT 进行身份认证，密钥由 `.env` 文件中的 `JWT_SECRET_KEY` 控制。  
> **如果保留默认值 `change_this_secret_in_env`，后端会在启动时直接报错退出，拒绝运行。**  
> 请在部署前务必：
> - 在项目根目录创建或修改 `.env` 文件；
> - 设置一个足够随机、长度较长的 `JWT_SECRET_KEY`（例如 32 位以上随机字符串）；
> - 重启后端服务。

**注意：需先启动后端，再启动前端，最后在浏览器打开前端地址。**

**1. 启动后端**

在项目根目录 `knowledge_platform` 下，使用已安装依赖的 Python 环境（如 conda）：

```bash
cd knowledge_platform
conda activate finance_agent   # 或你的环境，需已 pip install -r requirements.txt
uvicorn backend.app.main:app --reload --host 0.0.0.0
```

或使用脚本（会自动用 finance_agent 环境）：

```bash
cd knowledge_platform
./run_backend.sh
```

后端默认运行在：`http://127.0.0.1:8000`  
接口文档：`http://127.0.0.1:8000/docs`

**2. 启动前端**

新开一个终端：

```bash
cd knowledge_platform/frontend
npm install    # 首次需要
npm run dev
```

前端默认运行在：`http://localhost:5173`

**3. 登录**

浏览器打开 **http://localhost:5173**，使用默认管理员账号：

- 邮箱：`admin@example.com`（或数据库中为该账号配置的邮箱）
- 密码：`admin123`（首次使用建议通过系统管理修改为强密码）

**4. 常用地址**

- 前端页面：http://localhost:5173
- 后端健康检查：http://127.0.0.1:8000/health
- 接口文档（Swagger）：http://127.0.0.1:8000/docs

### 安全审计发现（待修复，2026-04-14）

> 说明：以下为本次代码审计识别的风险项，暂未修复。建议按优先级从高到低处理，并在修复后补充回归测试与变更记录。

#### Critical（优先立即修复）

- [ ] **上传路径穿越风险**（`backend/app/api/files.py`）

      当前以 `username == "admin"` 作为管理员兜底判定之一，属于字符串身份特判，存在权限模型绕过隐患。  
      建议：移除用户名特判，仅基于 `is_superuser` / 角色权限进行授权判断。

- [ ] **默认管理员弱口令硬编码**（`backend/app/main.py`、`scripts/create_admin.py`）  
      代码中存在默认管理员密码 `admin123` 与自动创建/重置逻辑，若在生产误用会导致高风险账号被猜解。  
      建议：移除硬编码默认密码，改为部署时一次性注入强密码并强制首登改密。

#### High（高优先级）

- [ ] **文件分享“只读”与“可下载”权限边界不严**（`backend/app/core/library_access.py`）  
      下载判定未严格区分 `FileShare.permission`（`read` / `download`），可能导致“仅预览分享”用户仍可下载原文件。  
      建议：在下载鉴权时针对文件级分享额外校验权限为 `download`。

#### Medium（中优先级）

- [ ] **预览 token 使用链路缺少实时 ACL 二次校验**（`backend/app/api/files.py`）  
      `preview-by-token` 校验 token 后直接返回文件，未按当前用户状态与最新权限关系重新校验访问权。  
      建议：按 token 中的 `user_id` 重查用户与 `can_access_file`，并考虑缩短 token 生命周期或引入可撤销机制。

- [ ] **登录接口缺少防爆破限速策略**（`backend/app/api/auth.py`）  
      当前未见按账号/IP 的失败次数限制、退避等待或临时锁定策略。  
      建议：增加速率限制、失败惩罚与安全告警审计。

- [ ] **前端 token 存储在浏览器存储中（XSS 放大面）**（`frontend/src/api/client.js`）  
      当前访问令牌保存在 `localStorage/sessionStorage`，若发生 XSS，令牌可能被窃取。  
      建议：评估迁移到 httpOnly + Secure + SameSite Cookie，并配套 CSRF 防护与 CSP 加固。

两种部署方式说明
----------------

### 方式 A：传统部署（Python + systemd + Nginx）

适用场景：

- 服务器环境以系统服务运维为主（不使用容器编排）
- 运维团队更熟悉 `systemd` / `nginx`
- 希望直接在宿主机管理 Python 虚拟环境与进程

对应资料：

- `deploy/.env.example.prod`
- `deploy/systemd/knowledge-platform.service`
- `deploy/nginx/knowledge-platform.conf`
- `docs/PROD_DEPLOY.md`

核心流程（简版）：

1. 拉代码并创建 `.venv`，安装依赖  
2. 配置 `.env`（JWT、数据库、存储、CORS）  
3. 执行 `alembic upgrade head`  
4. 启动 `systemd` 后端服务 + 配置 `nginx` 反代  
5. 验证 `GET /health`、登录、上传、预览、回收站

### 方式 B：镜像部署（Docker Compose）

适用场景：

- 希望环境一致、迁移简单、发布回滚更快
- 后续计划扩容或迁移到 K8s/容器平台
- 需要把应用、数据库、Nginx 以统一编排管理

对应资料：

- `docker/backend.Dockerfile`
- `docker/nginx.Dockerfile`
- `docker/entrypoint.sh`
- `docker/nginx.conf`
- `docker-compose.yml`
- `deploy/.env.example.docker`

核心流程（简版）：

1. 复制 Docker 环境变量模板：`cp deploy/.env.example.docker .env`  
2. 构建并启动：`docker compose up -d --build`  
3. 容器启动时自动执行 `alembic upgrade head`  
4. 通过 `http://服务器IP` 验证访问与核心功能

### 选型建议（当前项目）

- **优先建议**：方式 B（Docker Compose），更利于你后续“镜像部署到服务器”目标。
- 若当前运维限制无法容器化，可先用方式 A，上线稳定后再切换到方式 B。

领导班子权限与看板设计（评审骨架）
----------------

### 1. 设计目标与边界

- 适用范围：当前平台为“文件库 + 知识共享”，不包含审批流程。
- 保持现有规则：继续沿用库级 ACL（`visibility + LibraryMember + allow_download`）作为主判定链路。
- 新增能力定位：领导班子权限做“增量能力”，不推翻已有访问逻辑。
- 一致性要求：前端仅做展示收敛，后端接口必须执行最终鉴权。

### 2. 核心原则

- 同一套能力，不同数据范围（Scope）。
- 高管不等于超级管理员，默认不开放系统配置与权限模型改写能力。
- 组织调整时只改角色与分管映射，不改业务接口逻辑。
- 冲突规则固定：治理策略优先于日常操作；`deny` 优先于 `allow`。

### 3. 角色与范围模型（V1）

| 角色 | 建议代码 | 数据范围 | 定位 |
|------|----------|----------|------|
| 董事长 | `chairman` | `ALL` | 全局治理与监督 |
| 总经理 | `gm` | `ALL` | 全局经营管理与协同 |
| 副总经理 | `dgm` | `CUSTOM_DEPT` | 分管部门监督管理 |
| 书记 | `secretary` | `CUSTOM_DEPT` | 分管部门监督管理 |
| 部门负责人（部长） | `dept_leader` | `DEPT` | 部门日常管理 |
| 普通员工 | `employee` | `DEPT` / `SELF` | 文件使用与协作 |

> `CUSTOM_DEPT` 支持多部门，建议增加 `include_sub_dept` 以控制是否包含下级部门。

### 4. 董事长与总经理边界

- 共同点：均可查看全局看板并下钻查看全平台数据（受访问判定链路约束）。
- 董事长：偏治理权（策略、审计、例外授权、风险处置决策）。
- 总经理：偏经营权（运营指标、跨部门协同、执行跟踪）。
- 不建议默认让总经理直接改权限体系；权限配置权建议保留在董事长/平台管理员。

### 5. 领导班子管理逻辑（增量）

建议在现有角色字段之外引入以下控制维度：

- `view_scope`：查看范围（`ALL/CUSTOM_DEPT/DEPT/SELF`）。
- `manage_scope`：管理动作范围（默认 `NONE`，按需放开）。
- `manage_actions`：管理动作白名单，建议首批包括：
  - `freeze_library`（冻结资料库为只读）
  - `lock_download`（强制关闭导出）
  - `require_watermark`（强制水印策略）
  - `emergency_recover`（紧急恢复）

说明：以上动作属于“策略级/风险级”动作，不替代部长的日常管理动作。

### 6. 部长与分管领导的职责分层

- 部长（部门负责人）：负责部门日常运营管理（人员、部门库、日常维护）。
- 分管领导（副总/书记）：负责分管范围监督、风险治理与策略干预。
- 总经理/董事长：负责全局治理与跨部门统筹，不参与高频日常细项操作。

### 7. 领导看板设计（无审批场景）

建议新增“领导看板”入口，按范围自动出数：

- 董事长、总经理：全局看板（`ALL`）。
- 副总、书记：分管看板（`CUSTOM_DEPT`）。
- 部长：部门看板（`DEPT`，可复用看板组件）。

建议首批指标：

- 文件库总量、文件总量、近 7/30 天新增量。
- 按部门的活跃度（上传、预览、下载、分享趋势）。
- 受控预览占比、下载开关关闭占比（`allow_download=false` 覆盖率）。
- 回收站规模与异常（长期未处理、集中删除波动）。
- 审计风险项（高频删除、跨部门访问突增、敏感库访问波动）。

### 8. 接口映射口径（设计模板）

后续接口评审时，建议每个接口按以下模板标注：

- `接口名称`：例如 `GET /libraries/`
- `动作权限`：例如 `library:view`
- `范围校验`：`ALL/CUSTOM_DEPT/DEPT/SELF`
- `依赖现有 ACL`：是/否（默认是）
- `领导增量规则`：如“分管领导仅可见分管部门相关库”
- `审计要求`：是否必须记录审计日志

### 9. 审计与风控要求

- 所有领导层管理动作必须记录审计日志（操作者、范围、对象、前后值、时间、来源 IP）。
- 对冻结/限下载/紧急恢复类动作增加“二次确认 + 操作备注”。
- 看板导出、全局检索、跨部门下钻建议纳入重点审计事件。

### 10. 分阶段落地建议

- 第 1 阶段：完成角色范围与分管映射（不改现有 ACL 主链）。
- 第 2 阶段：上线领导看板（先只读与下钻）。
- 第 3 阶段：逐步开放少量治理动作（冻结/限下载等）并配齐审计。
- 第 4 阶段：根据实际使用反馈收敛权限边界，形成稳定版本并开放可视化权限配置页。

### 11. 待评审决策清单

- 敏感资料库是否对 `ALL` 范围自动可见，或需显式白名单授权。
- 总经理是否具备策略配置权，或仅保留经营分析与协同权限。
- 分管范围是否默认包含下级部门（`include_sub_dept` 默认值）。
- 领导是否允许直接执行删除类动作，或仅允许策略干预 + 审计闭环。
